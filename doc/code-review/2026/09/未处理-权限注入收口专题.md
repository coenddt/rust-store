## 1. 问题总览

一句话：**权限判定散落在 5 个独立函数里，各调用点各写各的——根路径调了 3 个、关联路径调了 0 个、computes 路径调了 4 个，因此出现"漏调即漏权"。**

| 组 | 问题 | 初判严重度 | 是否已进第 11 轮报告 |
|---|---|---|---|
| A | 关联（`$lookup`）节点四级权限全部未注入 | 疑似 B / C（越权） | ❌ 未收录 |
| B | 计算列权限两处缝隙 | M | ❌ 未收录 |
| C | owner 注入依赖固定字段名 `createdBy` + 伪角色 `creator`，不可配置 | M / I | ⚠️ 部分（B-11-2 只覆盖"门控"） |
| D | owner 注入门控（B-11-2）与 A/B/C 同源 | B | ✅ 已收录（B-11-2） |

## 2. A 组：关联节点权限四级缺失

### 2.1 结论表

| 检查项 | 根节点 | 关联节点（`$lookup` 内） |
|---|---|---|
| schema 级 `read` | ✅ `can_read_schema`（`command/query.rs:92-97`、`federation/plan/mod.rs:95-97`） | ❌ 不检查目标 schema（`build_lookup` 拿到 `n_schema` 后从不调用） |
| 关系定义级 `read`（`RelationDef.read`） | — | ❌ **完全不调用** `get_readable_relations` |
| 字段级 `read` | ✅ `apply_permission_prune`（`pipeline/projection.rs:13-27`） | ❌ `build_rel_projection` 只按请求字段加投影，不裁剪 |
| 行级 owner（`createdBy`） | ⚠️ 有注入但被 `$condition` 门控（B-11-2） | ❌ `lookup.rs` 内无 `merge_owner_condition` |
| 计算列 `read` | ✅ `get_readable_computes` → `build_add_fields`（`pipeline/lookup.rs:267-282`） | ❌ 目标 schema 的计算列同样不裁剪 |
| 关联附加条件 | — | ✅ 过 `validate_condition`（**拒绝名单，非权限**） |

### 2.2 代码证据（定位）

- 关联构建无任何权限调用：`pipeline/build.rs:86-113`（`root_lookup_stages`）、`pipeline/lookup.rs:89-125`（`ns_lookup_stages`）、`pipeline/lookup.rs:129-233`（`build_lookup`）。
- `get_readable_relations` 的**唯一调用点**是 `computes/run/sync.rs:173`——即"只有计算列链路认这条权限，查询链路不认"。（定义：`permission.rs:177-193`）
- 关系被无条件加入投影：`pipeline/projection.rs:138-142`。
- 关联投影不裁剪：`pipeline/lookup.rs:66-87`（`build_rel_projection`）。

### 2.3 为什么这是"缺陷"而不是"未实现功能"

关系级 `read` 是**已存在、已被使用**的正式配置，且在 computes 路径已实现：

- 定义：`schema::RelationDef.read`（`get_readable_relations` 逐条读取）。
- fixture 在用：`fixtures/computes/cases.json:208`（`"comments": { ... "read": ["admin"] }`）、`fixtures/computes/cases.json:240`、`:455`。
- 目标字段级限制也在 fixture 里：`fixtures/pipeline/cases.json:194`（`"ownerOnly": { "type": "string", "read": ["admin"] }`）。

→ 两条路径不一致 = **查询侧可绕过**。

### 2.4 可绕过的三种形态

1. 关系声明 `read:["admin"]`，普通用户 GQL 请求该关系 → 照样返回（越权读）。
2. 关联模型字段声明 `read:["admin"]` → 嵌套请求即得。
3. 关联模型声明 `read:["creator"]` → 既不校验 schema 级、也不注入 `createdBy` → 拿到**全部**关联行（不只自己的）。

## 3. B 组：计算列权限的两处缝隙

- **根级 computes.read：正常。** `build_add_fields(schema, ctx)` 按 `readable_computes` 跳过不可读计算列的 `$addFields`（`pipeline/lookup.rs:267-282`）。
- **缝 1（`$lookup` 阶段无 `ctx`）**：`build_compute_lookup_stages(schema)` 没有 `ctx` 参数（`pipeline/lookup.rs:235-265`），调用点 `pipeline/build.rs:163`。→ 所有计算列的底层 `$lookup` 都会构建执行；不可读计算列的数据"看不见"但**确实被查出来了**，属"靠投影兜底、非硬隔离"，同时是无效 IO。
- **缝 2（depends 不检查可读性）**：`append_compute_deps`（`pipeline/projection.rs:29-65`）把计算列 `depends` 字段并入投影时不校验该字段是否可读，依赖后续应用层（`computes/run/sync.rs` 的 `readable_fields`）再裁。

## 4. C 组：owner 注入依赖固定字段（不可配置）

### 4.1 两个硬编码约定

1. **触发**：`schema.read`（写侧 `has_creator_permission` 还看 `schema.write`）中出现字面伪角色 `"creator"`（`permission.rs:220-244`、`command/write.rs:135-142`）。
2. **字段**：字面量 `"createdBy"`，值固定取 `ctx.user_id`。

| 用途 | 位置 | 代码 |
|---|---|---|
| 读注入 | `permission.rs:255` | `json!({ "createdBy": ctx?.user_id })` |
| 读匹配 | `permission.rs:130` | `d.get("createdBy")` |
| 写填充 | `command/write.rs:79-82` | `doc.insert("createdBy", uid)` |
| upsert 填充 | `command/mutate/upsert.rs:94`、`:211` | `setOnInsert.insert("createdBy")` |
| 写探针投影 | `command/write.rs:194` | `{ "_id": 1, "createdBy": 1 }` |

- **无可配置项**：全仓 grep `ownerField` / `owner_field` / `ownerKey` / `creatorField` / `creator_field` → 0 匹配。
- **隐性耦合**：schema 必须自行声明 `createdBy` 字段。注入的 `{createdBy: uid}` 经 `scalar_column` 对未声明字段走 default 分支仍生成 `WHERE t."createdBy" = ?`，但关系模型的列是按 `fields` 展平建的——schema 未声明时 SQL 侧无此列，运行期才报 unknown column；core 注册期无「`read:["creator"]` ⇒ 必须声明 `createdBy`」校验。

### 4.2 owner 注入门控（与已收录的 B-11-2 同源）

- 单库：`command/query.rs:193-205` —— `if let Some(r) = ast.params.get("condition")` 才注入。
- 联邦：`federation/plan/mod.rs:100-112` —— 同款门控（复制粘贴），**两条路径都要修**。
- count：`command/count.rs:77` —— **无条件**注入（反证门控是 bug 而非设计）。
- 交叉反证：`py-store/src/py_store/permission.py` 镜像 + `py-store/tests/test_py_store.py:113-114` 断言 `merge_owner_condition(s, ctx, None) == {'createdBy':'u1'}`，即"无条件时 owner 单独作为条件"是各方一致预期语义。

## 5. 影响面（分仓库）

三仓关系：`rust-store` 是引擎（`core` + 绑定 `core-node`/`core-py`），`nodejs-store` / `py-store` 是 Host——SQL 翻译由 core 的 `dialectTranslate` 产出，Host 只负责"绑参 + 执行"。

| 仓库 | 角色 | 与本专题的关系 |
|---|---|---|
| `rust-store/core` | 根因所在 | 全部 A/B/C 组的代码在此 |
| `rust-store/core-node` | 薄绑定 | 经 `planQuery` / `dialectTranslate` 原样透出，无本地校验/缓解 |
| `rust-store/core-py` | 薄绑定 | 同上 |
| `nodejs-store` | Host | `crud/query.js:48` 直接转发 `core.planQuery`；`datasource.js:218` 走 `dialectTranslate`；`src/permission.js` **不含 owner 逻辑** → 无法在 Host 侧自救 |
| `py-store` | Host | `crud/query.py:54` 转发 `core.plan_query`；`executors/*.py` 走 `dialect_translate`；`permission.py` 仅是镜像 |

> 注：`nodejs-store` / `py-store` 各有独立评测报告（`已完成-nodejs-store评测报告.md`、`已完成-py-store评测报告.md`），本专题**未复评**这两仓；上表"受影响"是按调用链推导的暴露面。

## 8. 建议处理方案

1. **统一收口层（推荐主方案）**：把权限判定集中到一处（如 `permission::guard_query(ast, registry, ctx)`），在 pipeline 构建前对所有节点（根 / 每个 relation / 每个 compute）统一执行 `schema → relation → field → owner` 四级检查，避免"这条路径忘了调"。
2. **关联节点补齐四级检查**：`build_lookup` / `ns_lookup_stages` / `build_rel_projection` 接入目标 schema 的 `can_read_schema`、`get_readable_relations`、`get_readable_fields` 与 `merge_owner_condition`。
3. **计算列 `$lookup` 加 `ctx`**：不可读则不构建阶段（治缝 1）；`depends` 并入投影前校验可读性（治缝 2）。
4. **owner 收口 + 参数化**（可选，破坏性变更）：抽出 `apply_owner_filter(schema, ctx, params, ast)` 供单库/联邦/count 统一调用；`Schema.owner_field` 默认 `"createdBy"`；补注册期校验「`read:["creator"]` ⇒ 声明 owner 字段」。需三仓同步并在 CHANGELOG 声明。
5. **回归锚点**：为 P-1~P-4 各补一条对拍用例，纳入 CI 边界矩阵（否则后续会以别种形式复发）。
