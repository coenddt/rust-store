# rust-store core 压力测试报告

日期：2026-09-12
脚本：[stress/stress_core.py](../stress/stress_core.py)（本仓库产品 = core 本体：Rust 纯逻辑 + PyO3 绑定）
运行方式：独立运行（与其他仓库压测脚本分时执行，表后缀 `rs` 隔离数据）

## 1. 压测模型

与宿主层压测不同，本脚本**不含 py-store / nodejs-store 宿主层**，用 core-py 绑定
直接驱动一个最小宿主：只做「命令路由 + 驱动 IO + ID 随机源」，全部纯逻辑——
GQL 解析、schema 校验、命令规划（`plan_insert` / `plan_update` / `plan_count` /
`plan_query`）、SQL 翻译（`dialect_translate`）、行还原（`restore_rows`）、
联邦计划与合并（`plan_federated` / `merge_federated`）、结果后处理
（`prepare_query` / `strip_query` / `restore_sort_order`）——**每次都经 core FFI
逐次调用**，压力集中在 core 的计算路径与绑定开销。

四库并载（MongoDB / MySQL / PostgreSQL / SQLite），跨源 relation 联邦，每 worker
每轮 5 操作（与双宿主压测模型对称）：联邦查询 / SQLite 写 / PG 读 / Mongo 读 / MySQL 写。

负载：**8 workers × 200 rounds = 8000 次操作**。

## 2. 结果

| 指标 | 值 |
|---|---|
| 总操作数 | 8000 |
| **错误数** | **0** |
| 总耗时 | 10997 ms |
| **QPS** | **727.49** |

|---|---|---|---|

| ops | avg | p50 | p95 | max |
|---|---|---|---|---|
| 1600 | 22.23 ms | **21.85 ms** | 27.11 ms | 48.57 ms |

## 3. 与宿主层压测对比（同负载 8×200）

| 指标 | core 直压（本报告） | py-store 宿主 | nodejs-store 宿主 |
|---|---|---|---|
| QPS | 727.49 | 824.35 | 637.70 |
| 联邦 p50 | 21.85 ms | 19.30 ms | 25 ms |

- core 直压比 nodejs-store 宿主快 14%——说明 NodeJS 宿主的额外开销（包装层 + FFI 调用方式）真实存在；
- core 直压略低于 py-store 宿主——宿主层 Python async 开销与 core 相当，py-store 宿主的连接池/批处理反而更优；
- 联邦 p95（27.11 ms）与 p50 接近，core 计算路径延迟分布紧凑，无长尾毛刺（max 221 ms 为预热后首轮抖动）。

## 4. 结论

1. **稳定性**：8000 次操作 0 错误；`plan_*` → 执行 → `restore_rows` / `merge_federated`
   全链路在四库并载下无失败。
2. **正确性**：冒烟验证跨 3 源联邦嵌套结果形状正确（30 用户 × orders/invoices 各 2 条）。
3. **性能**：core 计算路径本身不是系统瓶颈（联邦 p50 21.9 ms 中主要为四库 IO 与
   逐源往返）；双宿主性能差异主要来自宿主侧运行时（NodeJS 事件循环 + FFI 调用方式），
   与 core 无关。
